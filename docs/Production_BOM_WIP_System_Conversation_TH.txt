ผู้ใช้:
คือเรากำลังทำรับบไลน์ผลิต ที่ต้องผูก Bomเพื่อไปวางแผนใหญ่ และนำแผนใหญ่ไปวางแผนย่อย และแตกออกมาว่าต้องใช้วัตถุดิบอะไรบ้างปกติ ถ้าง่ายๆก้แบบนี้ แต่ทีนี้ โรงงานเราเปนแบบนี้  สมมุติ เราจะผลิตสับปะรด 200 Kg   และมี wip 2 wip และraw อื่นอีก 10-20 รายการ  แต่ทั้งหมดนี้เวลาแตกออกมามันต้องแตกแยกกันเพราะวัตถุดิบมันไปคนละห้องกัน  เช่น wip1  ไปห้องตีแผ้ง วัตถุดิบที่ผูกกับ wip1และwip1 ก้จะแสดงออกมา1ใบ   ส่วน wip2อาจจะไปห้องป้ายแยม raw ที่ผูกกับ wip2 ก้ต้องแสดงมาอีก 1 ใบ  ส่วน Rawอื่นๆ 5 raw อาจจะไปห้องแพ็คก้จะแสดงอีกใบ  อีก10ิอาจจะไปห้อง บรรจุ หรืออื่นๆก้จะแสดงอีกใบ  และถ้าเกิดเราวาง ผลิตภัณฑ์ คนละตัว แต่ละตัวก้ต้องแยกกัน  แต่wip ของ sku1 กับ sku2  อาจจะมีบาง wip ที่ไปใบเดียวกันได้ไปห้องเดียวกัน  และ วัตถุดิบแต่ละตัว คนที่เบิกก็ไม่ใช่คนเดียว อาจจะต้องระบุเจ้าของวัตถุดิบแต่ละอันด้วย คือมันซ้ำซ้อนเยอะมากเลย ลองแนะนำมาที ว่าแบบ มาตราฐาน มันทำยังไง ลองออแบบระบบ แบบสรุปมาที flow

ผู้ช่วย:
สิ่งที่คุณเจอ จริงๆ คือ “โรงงาน Process Manufacturing + Multi-stage WIP + Multi-room Picking” ซึ่ง ERP ทั่วไปถ้าทำแบบ BOM ตรงๆ จะพังทันที เพราะโลกจริงไม่ได้มีแค่ “ผลิตสินค้า = แตก Raw”

เป้าหมายของระบบ:
ต้องการสร้างระบบวางแผนการผลิตสำหรับโรงงานอาหาร/กระบวนการผลิตที่มีหลายขั้นตอน โดยไม่ใช่แค่ระบบ BOM อย่างเดียว แต่เป็นระบบ Production Planning + Routing + Material Dispatch ที่สามารถวางแผนใหญ่ แตกแผนย่อย คำนวณ WIP/Raw/Pack และออกใบเบิกแยกตามห้อง/คน/กลุ่มเบิกได้

โจทย์จริง:
เมื่อวางแผนผลิตสินค้า FG เช่น สับปะรด 200 kg ระบบต้องแตกออกเป็น WIP หลายตัว เช่น WIP แผ่นขนม, WIP แยม และ Raw/Pack อีกหลายรายการ แต่รายการเหล่านี้ไม่ได้ไปที่เดียวกัน ต้องแยกไปตามห้อง เช่น ห้องตีแป้ง ห้องป้ายแยม ห้องแพ็ค ห้องบรรจุ หรือห้องอื่นๆ

ปัญหาสำคัญ:
1. สินค้า 1 ตัวมี WIP หลายตัว
2. WIP แต่ละตัวมีสูตรย่อยของตัวเอง
3. Raw บางตัวผูกกับ WIP คนละตัว
4. Raw แต่ละตัวไปคนละห้อง
5. คนเบิกวัตถุดิบแต่ละกลุ่มอาจไม่ใช่คนเดียวกัน
6. สินค้าหลาย SKU ที่วางแผนพร้อมกัน อาจมี WIP บางตัวที่ใช้ร่วมกันได้
7. WIP/Raw ที่ไปห้องเดียวกัน อาจต้องรวมใบเบิกเดียวกัน
8. บางรายการต้องแยกใบ เพราะคนละห้อง คนละเจ้าของ หรือคนละกลุ่มเบิก
9. Planner ไม่ควรต้องมาแยกใบเอง ระบบต้องแตกและ group ให้อัตโนมัติ

แนวคิดหลัก:
ห้ามทำ BOM แบบ FG -> Raw อย่างเดียว เพราะ BOM อย่างเดียวไม่รู้ว่า Raw ไปห้องไหน ใครเบิก รวมใบกับใครได้ หรือใช้ในขั้นตอนไหน

5) Logic การแตกใบเบิก
================================================================================

Input:
- Production Plan: ผลิตอะไร จำนวนเท่าไร วันที่ไหน กะไหน
- BOM: สูตรของ FG/WIP
- Routing: ขั้นตอนและห้อง
- Material Allocation: วัตถุดิบไปห้องไหน ใครเบิก คลังไหน กลุ่มไหน

Process:
1. For each production plan line:
   - explode BOM จาก FG ลงไปถึง WIP/RAW/PACK
2. ถ้าเจอ WIP:
   - สร้างความต้องการผลิต WIP
   - แตก BOM ของ WIP ต่อ
3. คำนวณปริมาณใช้จริง:
   - required_qty = plan_qty * bom_qty
   - ปรับด้วย yield/scrap/loss ถ้ามี
4. หา work_center:
   - จาก Routing ของ WIP/FG
   - หรือจาก Material Allocation ถ้ากำหนดเฉพาะ material
5. หา owner/picker/store/picking_group:
   - จาก Material Allocation
6. รวมรายการ:
   GROUP BY:
   - plan_date
   - shift
   - work_center
   - owner
   - picking_group
   - store_location
   - issue_timing
7. สร้างใบเบิก:
   1 group = 1 picking document
8. ในแต่ละใบ แสดงรายละเอียดว่าวัตถุดิบมาจากแผนผลิต SKU ไหนบ้าง เพื่อ trace กลับได้

Output:
- ใบเบิกห้องตีแป้ง
- ใบเบิกห้องแยม
- ใบเบิกห้องแพ็ค
- ใบเบิกห้องบรรจุ
- ใบเบิกอื่นๆ ตาม group

9) Pseudo Logic สำหรับ Developer

function generatePicking(planDate, shift):

    plans = getProductionPlans(planDate, shift)

    allRequirements = []

    for plan in plans:
        exploded = explodeBOM(plan.fg_item, plan.qty)

        for line in exploded:
            workCenter = findWorkCenter(line)
            allocation = findMaterialAllocation(line.material, line.parent_or_wip)

            requirement = {
                plan_id: plan.id,
                source_fg: plan.fg_item,
                parent_item: line.parent_item,
                material: line.child_item,
                qty: line.required_qty,
                uom: line.uom,
                work_center: allocation.work_center or workCenter,
                owner: allocation.owner,
                store: allocation.store_location,
                picking_group: allocation.picking_group,
                issue_timing: allocation.issue_timing
            }

            allRequirements.append(requirement)

    grouped = groupBy(
        allRequirements,
        plan_date,
        shift,
        work_center,
        owner,
        store,
        picking_group,
        issue_timing,
        material
    )

    createPickingDocuments(grouped)

หน้าผูก BOM ไม่ควรซับซ้อนเกินไป แต่ต้องรองรับ Multi-level

- สถานะ Active/Inactive
- หมายเหตุ

ส่วน Detail:
- ลำดับ
- รหัสวัตถุดิบ/ลูก
- ชื่อลูก
- ประเภทลูก เช่น WIP/RAW/PACK
- จำนวนใช้
- หน่วย
- Scrap %

11) สรุปสุดท้ายสำหรับ AI/Developer
================================================================================

ระบบที่ต้องสร้างไม่ใช่แค่ BOM System แต่เป็นระบบ Production Planning + Routing + Material Dispatch

แกนของระบบคือ:
Item → BOM → Routing → Production Plan → BOM Explosion → Material Allocation → Group by Room/Owner/Store/Picking Group → Generate Picking → Production

BOM = สูตร
Routing = ขั้นตอนและห้อง
Work Center = ห้อง/จุดผลิต
Material Allocation = ตัวกำหนดว่า Raw/Pack/WIP ไปห้องไหน ใครเบิก อยู่คลังไหน และรวมใบกับใคร
Picking List = ผลลัพธ์จากการคำนวณ ไม่ใช่ข้อมูลตั้งต้น

ถ้าจะออกแบบให้ใช้งานจริง:
- เริ่มจาก Item Master
- ทำ BOM ให้สะอาด
- ทำ Routing แยกจาก BOM
- ทำ Material Allocation ให้ละเอียด
- ให้ระบบแตกใบเบิกอัตโนมัติตาม group
- รองรับ WIP ใช้ร่วมกัน
- รองรับหลาย SKU ในแผนเดียว
- รองรับหลายห้อง หลายเจ้าของ หลายคลัง
- ต้อง trace กลับไปหาแผนผลิตและ SKU ต้นทางได้เสมอ

12) ส่วนเพิ่ม: Flow แผนกกลางแบบรวมแผนรายวันตามวัตถุดิบที่รับผิดชอบ
================================================================================

วัตถุประสงค์:
รองรับกรณีที่มี "แผนกกลาง" 1-2 แผนก (หรือมากกว่า) ทำหน้าที่วางแผนเบิกวัตถุดิบของตัวเอง
โดยอ้างอิงจากแผนย่อย/WIP ของทุกแผนกผลิตปลายทาง แล้วค่อยจ่ายให้แต่ละแผนกตามวันใช้งานจริง

ตัวอย่างภาพรวม:
- แผนกกลาง A รับผิดชอบ: น้ำตาล
- แผนกกลาง B รับผิดชอบ: แป้ง/น้ำมัน
- แผนกปลายทาง: ขาไก่, บิสกิต, นมแท่ง, ข้าวเกรียบ

Flow การทำงาน:
1. แผนกปลายทางวางแผนย่อย/WIP ตามวันและกะ
2. ระบบแตกความต้องการวัตถุดิบจากแผนย่อย (BOM Explosion)
3. ระบบ map วัตถุดิบแต่ละรายการไป "แผนกกลางเจ้าของวัตถุดิบ" ผ่าน Material Allocation
4. ระบบรวมยอดรายวันให้แผนกกลาง:
   GROUP BY:
   - owner_department (แผนกกลาง)
   - material_item
   - plan_date
   - shift (ถ้าต้องการ)
5. แผนกกลางเห็น "แผนรวมวัตถุดิบรายวัน" ของตัวเอง:
   - ยอดต้องใช้รวม
   - ยอดคงเหลือ
   - ยอดที่ต้องเบิกเพิ่ม
   - สถานะพอ/ไม่พอ
6. แผนกกลางยืนยันแผนเบิก (Daily Material Plan)
7. ระบบแตกจ่ายต่อเป็นรายการย่อยให้แต่ละแผนกปลายทาง (Allocation/Dispatch)
8. เมื่อจ่ายจริง ระบบ update สถานะกลับไปยังแผนย่อย/WIP ต้นทาง เพื่อ trace ได้

ผลลัพธ์หลัก:
- เอกสารแผนเบิกรวมของแผนกกลางต่อวัน (ต่อวัตถุดิบ)
- เอกสาร/รายการจ่ายแยกปลายทาง (แผนกไหนได้เท่าไร)
- มุมมองคงค้าง: รอจ่าย/จ่ายบางส่วน/จ่ายครบ

function generateOwnerDailyPlan(planDate, shift):

    subplans = getConfirmedSubplans(planDate, shift)
    exploded = explodeSubplanMaterials(subplans)

    for each line in exploded:
        ownerDept = mapOwnerDepartment(line.material_item)
        append demand row by:
            ownerDept,
            material_item,
            source_department,
            source_subplan,
            required_qty

    grouped = groupBy(
        ownerDept,
        material_item,
        planDate,
        shift
    )

    for each group:
        onhand = getOnhand(group.material_item, ownerDept)
        totalRequired = sum(group.required_qty)
        toIssue = max(totalRequired - reservedOrPreparedQty, 0)
        shortage = max(toIssue - onhand, 0)
        create owner_daily_material_plan_line
        create trace rows (owner_daily_material_demands)

function generateOwnerDispatch(ownerPlanId):

    lines = getOwnerPlanLines(ownerPlanId)
    for each line:
        demands = getDemandDetails(line)
        allocate issue qty by priority rule:
            due_date asc, priority desc, created_at asc
        create owner_dispatch_lines
        update allocated_qty / balance_qty in demand rows
    update status owner plan
