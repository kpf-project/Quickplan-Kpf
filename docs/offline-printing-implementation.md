# เอกสารสรุปการปรับปรุงระบบพิมพ์ใบบันทึกแบบออฟไลน์ (Offline Printing Implementation Details)

เอกสารฉบับนี้จัดทำขึ้นเพื่อแสดงรายละเอียดในการปรับปรุงโค้ดและโครงสร้างการทำงานในโครงการ **KPF Production Line** เพื่อรองรับการพิมพ์ใบบันทึก (Piece Rate Slip) จากเครื่องพิมพ์ภายในของอุปกรณ์ **Sunmi V3** ได้อย่างสมบูรณ์แบบในสภาวะที่ไม่มีการเชื่อมต่ออินเทอร์เน็ต (Offline Mode) โดยข้อมูลที่พิมพ์ออกมาจะมีหมายเลขเอกสาร (`docNo`) และไอดี (`id`) ที่ตรงกันกับการบันทึกในฐานข้อมูลเมื่อระบบซิงก์ข้อมูลกลับแบบ 100%

---

## 1. ปัญหาเดิมและหลักการออกแบบใหม่

### ปัญหาของระบบเดิม:
1. **การข้ามขั้นตอนการพิมพ์เมื่อออฟไลน์**: ระบบสแกนรายชิ้น (Piece Rate Scan) เดิมเมื่อตรวจพบว่าออฟไลน์ จะนำข้อมูลลงในถังพัก (Outbox) ของ IndexedDB ทันที แล้วข้ามส่วนการสั่งพิมพ์กระดาษไป
2. **ความไม่เข้ากันของเลขที่เอกสาร**: หมายเลขเอกสาร (`docNo`) ฝั่งออนไลน์ถูกสร้างโดยฟังก์ชันของ Postgres SQL ในฐานข้อมูลทำให้เครื่องไคลเอนต์ไม่สามารถรู้เลขที่จะได้ล่วงหน้าขณะออฟไลน์ ส่งผลให้ไม่สามารถพิมพ์เลขเอกสารที่ตรงกันได้

### สถาปัตยกรรมป้องกันการชนกันของเลขเอกสารแบบออฟไลน์ (Zero-Collision Architecture):
* **การใช้ Local Counter ควบคู่กับ Server Counter**:
  * เมื่ออุปกรณ์ออนไลน์และเชื่อมต่ออินเทอร์เน็ตเพื่อซิงก์ข้อมูลมาสเตอร์ (Offline Master Sync) ระบบจะส่งรอบล่าสุด (`last_round`) และลำดับสูงสุดล่าสุด (`last_seq`) ของเครื่องพิมพ์เครื่องนั้น ๆ จากฐานข้อมูลกลาง ลงมาบันทึกเก็บไว้ใน `localStorage` ของอุปกรณ์
  * เมื่ออุปกรณ์ออฟไลน์และบันทึกรายการผลิต ตัวอุปกรณ์จะอ่านรอบและลำดับจาก `localStorage` มาทำการบวกเพิ่มทีละ 1 รายการ และจัดเก็บกลับเข้าไปในอุปกรณ์ทันที ป้องกันไม่ให้เลขถอยหลังหรือซ้ำกันในเครื่องเดิม
* **เลขเอกสารแบบจำแนกตามอุปกรณ์ (Device-Partitioned Document Numbers)**:
  * รูปแบบเลขเอกสารออฟไลน์: `[MACHINE_CODE][YY]R[ROUND][SEQUENCE]` (เช่น `P0126R1000005` สำหรับเครื่อง `P01`, ปี พ.ศ. 2569, รอบ 1, ลำดับ 5)
  * โครงสร้างนี้ใช้รหัสประจำตัวของเครื่องชั่ง/เครื่องพิมพ์ตัวนั้น ๆ เป็นตัวแยกหมวดหมู่ (Partition) ทำให้เลขที่เอกสารของแต่ละเครื่องแยกจากกันอย่างเด็ดขาดและไม่มีวันชนกันในระดับฐานข้อมูลหลัก แม้อุปกรณ์ทุกเครื่องจะทำงานแบบออฟไลน์พร้อมกัน
* **การควบคุม Primary Key ด้วย UUID จากไคลเอนต์**:
  * ตัวแปร `id` (Primary Key) และ `requestId` จะถูกเจเนอเรตแบบสุ่มเป็น UUIDv4 ตั้งแต่วินาทีที่กดบันทึกที่หน้าเครื่อง และบันทึกเข้าไปในระบบออฟลน์ จากนั้นเมื่ออุปกรณ์กลับมาออนไลน์ ข้อมูลใน Payload ชุดเดิมจะถูกซิงก์ขึ้นเซิร์ฟเวอร์โดยไม่ผ่านกระบวนการแปลงไอดีใหม่ ทำให้มั่นใจได้ว่าข้อมูลในกระดาษและฐานข้อมูลมี Unique ID เดียวกัน

## 3. การรวมเลขเอกสารเป็นตัวนับต่อเครื่องตัวเดียว (Unified Per-Machine Document Numbers)

ระบบได้รับการปรับปรุงครั้งใหญ่เพื่อรวม NameSpace ของเลขเอกสารที่เคยแยกเป็น 2 ระบบ (ออนไลน์ใช้ Counter กลาง Scope `"PR"` และออฟไลน์ใช้ Counter ต่อเครื่อง) ให้เหลือเพียง **ตัวนับต่อเครื่องตัวเดียวและรูปแบบเลขเอกสารเดียวทั้งระบบ** ดังนี้:

### รูปแบบเลขเอกสารใหม่ (ใช้ทั้งออนไลน์และออฟไลน์):
* รูปแบบ: `[MACHINE_CODE][YY][MM][SEQ7]` (เช่น เครื่อง `P01`, ปี พ.ศ. 2569, เดือน 07, ลำดับ 5 → `P0169070000005`)
  * `YY` = ปี พ.ศ. 2 หลัก (อ้างอิง Timezone Asia/Bangkok)
  * `MM` = เดือน 2 หลัก (อ้างอิง Timezone Asia/Bangkok)
  * `SEQ` = ลำดับ 7 หลัก Zero-Pad
* **ไม่มีส่วน R/round ในเลขเอกสารอีกต่อไป** ตาราง Counter ยังคงเก็บคอลัมน์ `last_round` ไว้แต่ใช้ค่าคงที่ `1` เสมอ
* เพดานลำดับ (SEQ) ขยายจาก 100,000 เป็น **9,999,999** เมื่อเลขเต็มเพดานระบบจะหยุดและแจ้งผู้ดูแลระบบ (ไม่วนกลับไปเริ่มที่ 1 หรือเพิ่มรอบอีก)
* ตัวนับอยู่ที่ตาราง `production_daily_work_doc_counters` แถวต่อ `(machine_code จริง, year_be)` — เลิกใช้ Scope `"PR"` สำหรับเอกสาร Piece Rate ทั้งหมด ทำให้เลขที่ออกออนไลน์และออฟไลน์วิ่งอยู่บนตัวนับเดียวกัน ไม่ชนกัน

### Migration ฐานข้อมูล:
* **ไฟล์**: [20260727100000_unify_piece_rate_doc_numbers.sql](file:///C:/Users/Riew/Desktop/KPF/Production-Line/Production-Line/supabase/migrations/20260727100000_unify_piece_rate_doc_numbers.sql)
* **การแก้ไข**:
  1. เพิ่ม RPC `next_piece_rate_doc_number(...)` — ออกเลขเอกสารแบบ Atomic ผ่าน `INSERT ... ON CONFLICT (machine_code, year_be) DO UPDATE` โดยเพิ่ม `last_seq` ทีละ 1 (เพดาน 9,999,999 ถ้าเต็มจะ `RAISE EXCEPTION`) สร้างเลขในรูปแบบใหม่ และบันทึก Audit ลง `production_daily_work_doc_counter_audits` แบบ `on conflict (doc_no) do nothing` คืนค่า `{ doc_no, doc_round: 1, doc_seq, machine_code, year_be }`
  2. เพิ่ม RPC `raise_piece_rate_doc_counter(...)` — ยกระดับ Counter ฝั่งเซิร์ฟเวอร์แบบ Atomic ด้วย `last_seq = GREATEST(last_seq, p_seq)` (ไม่มีวันถอยหลัง) ใช้สำหรับซิงก์เลขจากอุปกรณ์ออฟไลน์และกลไก Raise-Before-Reserve แทนการอ่าน-แก้-เขียนจากโค้ดแอปเดิม
  3. ปรับ Check Constraint `last_seq` ของตาราง Counter และ `doc_seq` ของตาราง Audit ให้รองรับถึง 9,999,999
  4. ปรับ Check Constraint รูปแบบ `doc_no` ของตาราง Audit ให้รองรับ Pattern ใหม่ `^[A-Z0-9]{2,8}[0-9]{2}[0-9]{2}[0-9]{7}$` โดยยังคง Pattern เก่าทั้ง 2 แบบไว้เพื่อรองรับข้อมูลประวัติ
  5. เพิ่ม Partial Unique Index `production_piece_rate_logs_doc_no_active_uidx` บนคอลัมน์ `doc_no` เฉพาะเอกสารสถานะ `active` เพื่อกันเลขเอกสารซ้ำในระดับฐานข้อมูล (**คำเตือน**: หากมีข้อมูล `doc_no` ซ้ำค้างอยู่ในตาราง Index จะสร้างไม่ผ่าน ต้อง Dedupe ข้อมูลก่อน Deploy)

### กฎการทำงานร่วมกันระหว่างออนไลน์-ออฟไลน์:
* **Flush-First**: ก่อนบันทึกแบบออนไลน์ทุกครั้ง หากยังมีรายการค้างใน Outbox ระบบจะสั่ง Flush ซิงก์รายการค้างให้เสร็จก่อน (แสดงสถานะ "กำลังซิงก์ข้อมูลค้าง…") เพื่อให้เลขออฟไลน์ที่ค้างอยู่ถูกบันทึกก่อนเสมอ หาก Flush ไม่สำเร็จ (ยังออฟไลน์) จึงค่อยตัดสินใจเข้าสู่เส้นทาง Offline Queue
* **Raise-Local**: ทุกครั้งที่บันทึกออนไลน์สำเร็จ อุปกรณ์จะอ่าน `docSeq` จาก Response แล้วยกระดับ Counter ใน `localStorage` (`piece_rate_offline_counter_[MACHINE]`, รูปแบบ `{ lastRound: 1, lastSeq }`) ให้ทัดเทียมเซิร์ฟเวอร์ทันที (เขียนเฉพาะเมื่อเลขใหม่สูงกว่าเดิม)
* **Raise-Before-Reserve**: ตอนบันทึกออนไลน์ อุปกรณ์จะแนบ `docCounterHint: { lastSeq }` (ลำดับสูงสุดที่เครื่องเคยพิมพ์) ไปกับ Payload เซิร์ฟเวอร์จะเรียก `raise_piece_rate_doc_counter` ยก Counter ให้ทันเครื่องก่อนจองเลขใหม่ ป้องกันกรณีเครื่องเคยพิมพ์เลขออฟไลน์ที่สูงกว่า Counter บนเซิร์ฟเวอร์
* **Retry ก่อนตัดสินว่าออฟไลน์**: หากการ Submit ครั้งแรกล้มเหลวแบบกำกวม (ไม่มีผลลัพธ์ หรือสถานะ 0/408/425/429/5xx) ระบบจะ Retry ด้วย `requestId` เดิมอีก 1 ครั้ง หากสำเร็จหรือได้รับแจ้งว่าซ้ำ (Duplicated) พร้อมเลขเอกสารจริง จะนำเลขจริงนั้นไปพิมพ์แทนการเข้าคิวออฟไลน์
* เมื่อบันทึกออฟไลน์ อุปกรณ์สร้างเลขด้วยรูปแบบใหม่จาก Counter ในเครื่อง (บวกทีละ 1 ห้ามวนกลับ หากเกิน 9,999,999 จะบล็อกการบันทึกและแจ้งเตือน) และเมื่อซิงก์กลับ เซิร์ฟเวอร์จะแกะ Machine/YY/MM/SEQ จากเลขนั้นแล้วเรียก `raise_piece_rate_doc_counter` พร้อมบันทึก Audit

### การลบ Fallback `"P00"`:
* ทั้งหน้าจอสแกน (`PieceRateScanPageClient.js`), ฟอร์มบันทึก (`PieceRateWorkForm.js`) และฝั่งเซิร์ฟเวอร์ (`pieceRateWorkService.js`) **ลบค่า Fallback `"P00"` ออกทั้งหมด**
* หากไม่สามารถระบุรหัสเครื่องได้ หน้าจอจะแสดงสถานะ "ยังไม่ได้ตั้งค่ารหัสเครื่อง ไม่สามารถบันทึก/พิมพ์ได้" และบล็อกการบันทึกทั้งออนไลน์และออฟไลน์ ฝั่ง API จะตอบกลับ HTTP 400 เช่นเดียวกัน เพื่อบังคับให้ทุกเอกสารมีเครื่องต้นกำเนิดที่ชัดเจน

### หมายเหตุความเข้ากันได้กับข้อมูลเดิม:
* ข้อมูลประวัติที่ใช้เลขรูปแบบเก่า (ทั้งแบบ `YYMM+SEQ5` และแบบ `[MACHINE][YY]R[ROUND][SEQ6]`) ยังคงใช้งานและแสดงผลได้ตามปกติ Constraint ของตาราง Audit ยังรองรับ Pattern เก่าทั้ง 2 แบบ และ Unique Index ใหม่ไม่ได้ผูกกับรูปแบบเลข
* RPC `next_production_daily_work_doc_number` เดิมยังคงอยู่และยังใช้งานโดยฟีเจอร์อื่น (Daily Work, Pallet Scan, Snack Yield) ไม่ได้รับผลกระทบจากการเปลี่ยนแปลงครั้งนี้
