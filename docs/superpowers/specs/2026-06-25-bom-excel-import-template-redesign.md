# BOM Excel Import and Template Redesign

วันที่: 2026-06-25  
สถานะ: อนุมัติแนวทางแล้ว รอตรวจเอกสารก่อนจัดทำแผน implementation

## 1. เป้าหมาย

ปรับระบบดาวน์โหลดเทมเพลตและนำเข้า Excel ในหน้า BOM ไลน์การผลิตให้ตรงกับข้อมูลและกติกา BOM ปัจจุบัน โดยไฟล์เดียวต้อง:

- รองรับหลายสินค้าตัวแม่
- รองรับ BOM ของ FG และ BOM ของ WIP ในไฟล์เดียวกัน
- ใช้สูตรหลัก `DEFAULT` เท่านั้น
- เก็บรายละเอียดรายการเทียบเท่าการบันทึกจากหน้าเว็บ
- ตรวจสอบข้อมูลและแสดง Preview ก่อนเขียนข้อมูลจริง
- รองรับไฟล์เทมเพลตรุ่นเก่าเท่าที่สามารถแปลงได้อย่างปลอดภัย
- ไม่สร้างหรือแสดงข้อความ Mojibake

## 2. ขอบเขต BOM

### 2.1 ประเภทสินค้า

- FG: หมวด `04`, `04-1`, `04-2`
- WIP: หมวด `03`
- RAW: หมวด `01`, `02`, `05`, `08`, `10`

### 2.2 Matrix

- FG ใช้ WIP หรือ RAW ได้
- WIP ใช้ WIP หรือ RAW ได้ตามกติกาปัจจุบันของระบบ
- RAW เป็นสินค้าตัวแม่ของ BOM ไม่ได้
- ระบบต้องตรวจสินค้าตัวแม่และรายการลูกจากข้อมูลจริงใน `products_cache`

### 2.3 โครงสร้างหลายระดับ

แต่ละแถวแทนหนึ่งรายการลูกของสินค้าตัวแม่ เช่น:

| Parent | Component |
|---|---|
| `B03-0003` | `WKB-0041` |
| `WKB-0041` | `M01-00040` |
| `WKB-0041` | `M03-00220` |

เมื่อ import ระบบจะสร้างหรืออัปเดต BOM ของ `B03-0003` และ `WKB-0041` แยกกัน โดยการแตกโครงสร้างหลายระดับยังใช้กลไก BOM ปัจจุบัน ไม่บันทึกรายการ RAW ของ WIP ซ้ำเข้า BOM ของ FG

## 3. รูปแบบ Workbook

Workbook ประกอบด้วย:

1. `BOM-Input` สำหรับกรอกข้อมูล
2. `วิธีกรอก` สำหรับคู่มือและตัวอย่าง
3. `รายการสินค้า` สำหรับอ้างอิง FG และ WIP ที่เป็น Parent ได้
4. `รายการวัตถุดิบ` สำหรับอ้างอิง WIP และ RAW รวมรหัสการค้า
5. ชีตซ่อนสำหรับรายการ validation และสูตร lookup ตามความจำเป็น

รูปแบบใช้โทน Navy และ Gold ตามหน้าระบบ ตารางต้องอ่านง่าย มี Freeze Header, Filter, สีแยกช่องกรอกและช่องอัตโนมัติ และไม่พึ่งสูตร Excel รุ่นใหม่ที่ทำให้เปิดไม่ได้ในเครื่องหน้างานทั่วไป

## 4. คอลัมน์ `BOM-Input`

| คอลัมน์ | ฟิลด์ | การกรอก | กติกา |
|---|---|---|---|
| A | รหัสสินค้าตัวแม่ | ผู้ใช้กรอก | SKU ของ FG หรือ WIP |
| B | ชื่อสินค้าตัวแม่ | อัตโนมัติ | Lookup จากรายการสินค้า |
| C | ประเภทตัวแม่ | อัตโนมัติ | `FG` หรือ `WIP` |
| D | โหมดปริมาณ WIP | ผู้ใช้กรอก | `UNIT` หรือ `BATCH`; FG ใช้ `UNIT` |
| E | base_batch | ผู้ใช้กรอก | มากกว่า 0; FG และ WIP แบบ UNIT บังคับเป็น 1 |
| F | base_output_boxes | ผู้ใช้กรอก | มากกว่า 0 |
| G | รหัสวัตถุดิบที่ใช้จริง | ผู้ใช้กรอก | ใช้รหัสการค้าเมื่อมี มิฉะนั้นใช้ SKU |
| H | SKU ภายใน | อัตโนมัติ | Resolve จากรหัสการค้า |
| I | ชื่อวัตถุดิบ/WIP | อัตโนมัติ | ชื่อของรหัสที่เลือก |
| J | ประเภทลูก | อัตโนมัติ | `WIP` หรือ `RAW` |
| K | จำนวน | ผู้ใช้กรอก | มากกว่า 0 |
| L | หน่วย | อัตโนมัติ | หน่วยของรหัสการค้า/รายการที่เลือก |
| M | ฐานคำนวณ | ผู้ใช้กรอก | `JOB_QTY`, `HEADCOUNT`, `MACHINE_COUNT`, `DOUGH_SET_COUNT` |
| N | ค่าฐาน | ผู้ใช้กรอกตามเงื่อนไข | มากกว่า 0 เมื่อฐานคำนวณไม่ใช่ `JOB_QTY` |
| O | วิธีปัดเศษ | ผู้ใช้กรอกตามเงื่อนไข | `NONE`, `UP`, `DOWN`, `NEAREST` |
| P | วันเหลื่อมแผน | ผู้ใช้กรอกตามเงื่อนไข | จำนวนเต็ม `-30` ถึง `30`; ใช้กับ WIP |
| Q | หมายเหตุ | ไม่บังคับ | ข้อความธรรมดา |

ชื่อหัวคอลัมน์ภาษาไทยเป็นหลัก และ parser ต้องรองรับ alias ภาษาอังกฤษที่กำหนดไว้เพื่อความเสถียร ไม่อ้างอิงตำแหน่งคอลัมน์อย่างเดียว

## 5. การจัดกลุ่มและรายการซ้ำ

หน่วยของการ import คือ:

`Parent SKU + DEFAULT formula`

รายการลูกต้องใช้ key:

`material_sku_code + material_goods_code`

จึงอนุญาตให้ SKU เดียวกันปรากฏหลายรายการได้เมื่อเป็นคนละรหัสการค้า และห้ามรวมรายการดังกล่าวเข้าด้วยกันโดยใช้ SKU อย่างเดียว

ค่า config ของ Parent ได้แก่ `wip_qty_input_mode`, `base_batch` และ `base_output_boxes` ต้องตรงกันทุกแถวภายใน Parent เดียวกัน หากไม่ตรงให้ทั้ง Parent ไม่ผ่าน Preview

## 6. ค่าเริ่มต้นและไฟล์รุ่นเก่า

ไฟล์รุ่นเก่าที่มีคอลัมน์เดิมจะยังอ่านได้ โดยใช้ค่าเริ่มต้น:

- `formula_code`: `DEFAULT`
- `formula_name`: `สูตรหลัก`
- `material_goods_code`: ใช้รหัสจากคอลัมน์รหัสวัตถุดิบ
- `wip_qty_input_mode`: WIP ใช้ `BATCH`; FG ใช้ `UNIT`
- `calculation_basis`: `JOB_QTY`
- ค่าฐานจำนวนคน/เครื่อง/ชุดแป้ง: `1`
- วิธีปัดเศษ: `NONE`
- `planning_offset_days`: `0`
- หน่วย: Resolve จากข้อมูลวัตถุดิบในระบบ

หากรหัสจากไฟล์เก่าตรงได้หลายรหัสการค้า ระบบต้องไม่เดา ให้แสดงข้อผิดพลาดใน Preview และระบุว่าต้องเลือกรหัสการค้าให้ชัดเจน

## 7. Validation

Validation แบ่งเป็นสองชั้น:

### 7.1 Client parsing

- ตรวจชนิดไฟล์และพบชีตข้อมูล
- ตรวจหัวคอลัมน์ขั้นต่ำ
- แปลงตัวเลขโดยไม่เปลี่ยนรหัสสินค้าเป็นเลข
- เก็บเลขแถว Excel สำหรับแสดงข้อผิดพลาด
- ไม่ตัดแถวผิดทิ้งโดยไม่มีคำอธิบาย

### 7.2 Server validation

- ตรวจสิทธิ์ `production-line-bom-manage`
- Resolve Parent, SKU, รหัสการค้า, ชื่อ, ประเภท และหน่วยจากข้อมูลระบบ
- ตรวจ Matrix
- ตรวจค่าฐานสูตรและโหมด WIP
- ตรวจฐานคำนวณ ค่าฐาน วิธีปัดเศษ และวันเหลื่อม
- ตรวจรายการซ้ำด้วย composite key
- ตรวจวงจร BOM ที่เกิดจากข้อมูลในไฟล์ร่วมกับ BOM ปัจจุบันก่อนยืนยัน
- ใช้ validation ชุดเดียวกันทั้ง Preview และ Import จริง

ข้อมูลจาก Excel ที่เป็นชื่อ ประเภท หรือหน่วยถือเป็นข้อมูลช่วยแสดงผลเท่านั้น Server ต้องใช้ค่าที่ Resolve จากระบบเป็นค่าจริง

## 8. Preview

Preview ต้องแสดง:

- จำนวน Parent ทั้งหมด
- จำนวนรายการที่พร้อม import
- Parent ที่มีข้อผิดพลาด
- เลขแถว Excel และข้อความภาษาไทยที่อ่านรู้เรื่อง
- รหัส Parent, ประเภท, โหมด WIP และฐานสูตร
- รหัสการค้า, SKU, ชื่อ, จำนวน, หน่วย
- ฐานคำนวณ ค่าฐาน วิธีปัดเศษ และวันเหลื่อม
- Diff เพิ่ม/แก้ไข/ลบ เทียบกับสูตร `DEFAULT` ล่าสุด

ห้ามกดยืนยันเมื่อ Parent ใดมี validation error เพื่อหลีกเลี่ยงการ import แบบบางส่วนโดยไม่ตั้งใจ

## 9. การบันทึก

- Import ต้องสร้าง BOM Parent เมื่อยังไม่มี
- ต้องสร้างหรือยืนยันแถว `production_bom_formulas` สำหรับ `DEFAULT`
- สร้าง `production_bom_versions` ใหม่ แยกต่อ Parent
- บันทึกรายการลง `production_bom_items` ครบทุกฟิลด์
- สถานะและเงื่อนไขขออนุมัติต้องเหมือนการบันทึกจากหน้าเว็บ
- การเขียนข้อมูลของแต่ละ Parent ต้องเป็น atomic operation
- ถ้ามี Parent ใดล้มเหลวระหว่างเขียน ต้องรายงานชัดเจนและไม่ทิ้ง Version ที่มีรายการไม่ครบ

โหมด import ที่รองรับ:

- `Replace`: แทนรายการทั้งหมดของสูตร `DEFAULT`
- `Append`: รวมกับรายการล่าสุดโดยใช้ composite key

เมื่อพบ key ซ้ำ รองรับ:

- `Overwrite`
- `Skip`
- `Sum`

## 10. โครงสร้างโค้ด

ควรแยกความรับผิดชอบดังนี้:

- `bomExcel.js`: สร้างและ parse workbook
- โมดูล contract/normalization กลาง: ชื่อคอลัมน์ alias ค่า enum และ default
- โมดูล validation/merge กลาง: ใช้ร่วมกันระหว่าง Preview และ Import
- API Preview: resolve และตรวจข้อมูลโดยไม่เขียนฐานข้อมูล
- API Import: ใช้ผล normalization เดียวกันและเขียนข้อมูลแบบ atomic
- Preview Modal: แสดงผลครบทุกฟิลด์และไม่มี Mojibake

ไม่ควรทำ business validation หลักไว้เฉพาะใน `BomEditorPageClient.js`

## 11. Performance

- Lazy-load `exceljs` เฉพาะตอนดาวน์โหลดหรืออ่านไฟล์
- จำกัดจำนวนแถวและขนาดไฟล์ด้วยค่าที่ระบุชัดเจน
- Resolve Parent และ Component แบบ batch ไม่ query ต่อแถว
- ประมวลผล Preview เป็นกลุ่มและรักษาลำดับจากไฟล์
- ไม่โหลด catalog ซ้ำเมื่อข้อมูลพร้อมอยู่แล้ว

## 12. Security and Data Integrity

- ไม่เชื่อชื่อ ประเภท หน่วย หรือ SKU ที่ซ่อนอยู่ในสูตร Excel
- ตรวจสิทธิ์ที่ Server ทุก endpoint
- ไม่รับ `formula_code` อื่นนอกจาก `DEFAULT`
- ป้องกัน formula injection ในช่องข้อความที่ถูกเขียนกลับเข้า Excel
- จำกัดไฟล์เป็น `.xlsx` และไม่ประมวลผล macro
- ไม่บันทึกข้อมูลบางส่วนภายใน Parent เดียวกัน
- ไม่เปิดเผย service-role key ให้ Client

## 13. การแก้ Mojibake

ไฟล์ที่แก้ในขอบเขตนี้ต้องบันทึกเป็น UTF-8 และแก้ข้อความ Mojibake ใน:

- การแจ้งเตือนดาวน์โหลด/อ่านไฟล์/import
- Preview Modal
- ข้อความ validation และ diff ที่เกี่ยวข้อง
- คู่มือและหัวคอลัมน์ใน workbook

ต้องมี test หรือ static scan สำหรับข้อความเสียรูปที่พบบ่อยในไฟล์ขอบเขตนี้

## 14. การทดสอบ

- Parse เทมเพลตใหม่ครบทุกฟิลด์

- ตรวจ config Parent ไม่ตรงกัน
- ตรวจ enum และช่วงตัวเลข
- Merge แบบ Replace/Append และ Overwrite/Skip/Sum
- ปฏิเสธสูตรที่ไม่ใช่ `DEFAULT`

- Parent RAW ถูกปฏิเสธ

## 15. Definition of Done

- ดาวน์โหลดเทมเพลตใหม่จากหน้า BOM ได้
- กรอกหลายสินค้าและ BOM ของ WIP ในไฟล์เดียวได้
- Import แล้วข้อมูลทุกฟิลด์ตรงกับการบันทึกจากหน้าเว็บ
- สูตรทั้งหมดเป็น `DEFAULT`
- รหัสการค้าของวัตถุดิบไม่สูญหายหรือชนกันผิดรายการ
- Preview แสดงข้อผิดพลาดและ Diff ครบ
- ไฟล์เก่าที่แปลงได้ยังใช้งานได้
- ไม่มี Mojibake ในขอบเขตที่แก้
- Tests, lint และ build ผ่าน
